# Legacy document formats

The Godot port reads every shipped example from recovered text records. The prepared catalogs contain all 28 `.cem` experiments and all 46 `.cl3` structures and 59 extensionless model-library structures, retaining original file hashes and raw lines. `tools/prepare_legacy_formats.py` regenerates these catalogs with `uv run python tools/prepare_legacy_formats.py`. `LegacyFormats` implements the same record layouts in GDScript and returns dictionaries directly usable by the application.

## Experiment vessels (`.cem`)

Observed source: `recovered/native/main/decompiled.cpp`, `FUN_0042dc3c` at line 10670 (writer), `FUN_0043240c` at line 11821 (reader). Published save/open entry points call these functions (`published_recovered.cpp`, lines 10950 and 11095).

The first five lines hold the signature and four counters. Each of the first counter's vessel records contains 40 metadata lines, a reagent count, reagent triplets (name, grams, moles), a reaction count, and reaction records. A reaction has an identifier, title, reactant/product counts, name/coefficient pairs, and five parameter lines. Each vessel ends with 20 simulator values. The exported metadata exposes the vessel type ID, original x/y placement, capacity and temperature, and preserves all unlabelled fields. Original chemical state qualifiers and zero-quantity product entries are retained.

After vessels, the third header counter selects fixed 25-line connector records. The parser exposes their original endpoint positions and attached vessel names. Reagent-specific mass/mole variable names follow the connector section. Further custom variables, labels and plots remain in `trailing_lines` and `raw_lines`; these fields are preserved but their entire behavior has not been ported by this parser. `serialize_cem` reconstructs vessel/reagent/reaction/connector records with edited fields while retaining unknown metadata and the remaining trailer. Unchanged numbers retain original decimal formatting. This parser supports the supplied V3 documents; the native reader also contains compatibility branches for older signatures, which are not yet implemented.

## Molecule graphs (`.cl3`)

Observed source: `recovered/native/molecule/decompiled.cpp`, `FUN_0041fe4c` at line 8663, particularly lines 9256–9713. Header signature is `2107`. After 60 header lines comes an editor graph group count. Each group starts with a central-record count; each record occupies 46 lines: two central metadata integers, atom label, XYZ, and four 10-line neighboring atom/bond slots. Neighbor slots contain type, label, XYZ, bond order, bond label and direction vector. Atoms are deduplicated by stored label and bonds by endpoint pair. No distance-based bonds are invented.

The editor uses approximately ten graphic units per angstrom (e.g. ethanol's stored C–C separation is 15.4); the renderer-facing `position` divides editor coordinates by ten, while `legacy_position` retains original values. This scale is an inference from supplied geometry, not a declared unit in the file.

A second section holds imported/free structures (DNA and several crystal examples). Each has a title, atom count and bond count. Atoms occupy 109 lines (label, two radii, XYZ, RGB, 100 integer fields); bonds occupy 111 lines (label, endpoint XYZ pairs, RGB, radius, 100 integer fields). Explicit endpoint coordinates match stored atom positions to recover connectivity. Imported coordinates remain unscaled. Free structure bonds do not store a demonstrated chemical bond-order field; exported order defaults to one while preserving the original label and raw record.

The 46 `.cl3` structures produce 1,319 unique atoms and 1,299 bonds. The extensionless model-library files use a shorter layout: seven header lines, nine lines per atom (label, radii, color and XYZ), and seven per explicit bond (label and endpoint XYZ pairs). All 59 such shipped files are included in the same catalog, tagged `format: model`; their original text is retained. The combined catalog has 105 structures, 4,931 atoms and 4,960 bonds. Godot headless verification (`godot/tests/legacy_formats_test.gd`) parsed all 133 documents, matched catalog vessel/atom/bond counts, confirmed exact UTF-8 CRLF round trips and checked edited experiment positions. Original `.cem`/`.cl3` files use GB18030. `LegacyEncoding` now implements the complete two-byte mapping and four-byte Unicode ranges using generated `godot/data/gb18030.json`; `load_document` reads either UTF-8 or GB18030. All 133 shipped original files decode correctly and encode back to identical bytes. Original `.cem` exports also match their input bytes exactly when unchanged.

Encoding detection prioritizes valid UTF-8 for `.cem`/`.cl3`; extensionless `2107` model-library files prioritize GB18030 because a legacy two-byte Chinese sequence can also be valid UTF-8 with a different meaning. The codec's optional `prefer_gb18030` argument supports an explicit choice. Invalid byte sequences are rejected. The source document records its selected encoding; native exports retain it and default to GB18030 for prepared legacy catalogs.

Molecule serialization currently preserves original records unchanged; molecule geometry edits are saved in the new JSON format rather than exported to the legacy format.
